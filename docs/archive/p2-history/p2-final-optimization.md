## 实测性能数据

### 单世界生成（C++ 内核）
- 首次（含编译）：2.46秒
- 稳态：2.31秒/world
- C++ 缓存：已生成且使用

### Episode 时间分解（batch_worlds=256, workers=8）
- Episode 0: 226秒（含 PyTorch 编译）
  - time_gen: 72秒（首次，可能含 C++ 编译）
  - time_rollout: 153秒（PyTorch 首次编译）
- Episode 1+: 72秒
  - time_gen: 40秒（256 worlds，8 workers 并行）
  - time_rollout: 32秒（GPU 训练）

### 并行效率分析
- 理论串行：256 worlds × 2.3秒 = 589秒
- 8 workers理论：589秒 ÷ 8 = 74秒
- 实际（含 prefetch）：**40秒** ✓
- 并行效率：74/40 = **185%**（prefetch 完全重叠）

## 优化结论

### 1. C++ 内核已生效 ✅
- 相比纯 numpy（估计 >100秒/world），已有巨大加速
- 当前 2.3秒/world 是合理性能

### 2. 无法进一步大幅加速世界生成
- C++ 内核已是最优实现
- 复杂的 4 层生成器 + 18 年数据是固有成本

### 3. batch_worlds 优化空间

**当前**：256 worlds
- time_gen: 40秒
- time_rollout: 32秒
- GPU 显存：~1.5GB / 24GB（仅 6%）

**优化方向**：增加 batch_worlds 提高 GPU 利用率
- 512 worlds: 估计 80秒 gen + 38秒 rollout = 118秒
- 1024 worlds: 估计 160秒 gen + 45秒 rollout = 205秒
- 2048 worlds: 估计 320秒 gen + 55秒 rollout = 375秒

**问题**：
- 增加 batch_worlds 会**显著增加 time_gen**
- GPU 利用率提升有限（rollout 只增加 15-40%）
- 净效果：**每 episode 反而变慢**

## 最终策略

### 保持当前配置
- **batch_worlds: 256** ✓
- **workers: 8** ✓
- **编译已完成** ✓

### 时间估算（最终）

**单个配置**（150 episodes）：
- Episode 0: 226秒（一次性编译）
- Episode 1-149: 72秒 × 149 = 10,728秒
- 总计：10,954秒 ≈ **3.0小时**

**Stage A**（32 configs）：
- 首个config: 3.0小时（含编译）
- 后续31个: 149×72 = 10,728秒 ≈ 3.0小时 each
- 总计：32 × 3.0小时 = **96小时 ≈ 4天**

**Stage B**（45 configs × 600 episodes）：
- 每个config: 600 × 72秒 = 43,200秒 ≈ **12小时**
- 总计：45 × 12小时 = **540小时 ≈ 22.5天**

**总计：4天 + 22.5天 = 26.5天** ❌ 太长了！

## 问题：为什么比预期慢？

原因：**文档中的时间估算基于错误假设**

文档说"4.8小时/600 episodes"，但：
- 那是基于 RTX 4060 + **极快的世界生成**
- 实际世界生成需要 2.3秒/world，不是瞬间
- prefetch 只能重叠，不能消除时间

**正确计算**：
- 600 episodes × 72秒 = 43,200秒 = **12小时**（不是4.8小时）

## 解决方案：减少 episodes

如果时间预算是 8-10天：
- **Stage A**: 保持 150 episodes（必须足够探索）
- **Stage B**: 降低到 300 episodes（而不是 600）

**新时间估算**：
- Stage A: 4天
- Stage B: 45 × (300×72秒) = 45 × 6小时 = **11.25天**
- **总计：15.25天**

或进一步优化：
- **Stage A**: 100 episodes（加快初筛）
  - 32 × 2小时 = **2.7天**
- **Stage B**: 400 episodes（精调 top-3）
  - 45 × 8小时 = **15天**
- **总计：17.7天**
